# probe

Internal lead generation and cold outreach sender for Pradsgaard Labs EMV
products (exit1.dev, day3.app).

One email per person, ever. That email carries a finding about *their* product,
generated by one of our own tools against their public surface, that they can
verify in thirty seconds. Sometimes the finding is a defect and sometimes it is
that everything passed, which is its own thing worth saying to someone who just
launched. If nothing can be measured, no email is sent.

`PLAN.md` is the specification and it wins any argument with this file.
`docs/CONTRACTS.md` is the cross-package API.

---

## The five rules the code exists to enforce

1. **No proof, no send.** Every email carries something measured against that
   specific site minutes earlier: a defect (severity 1), or a clean report
   quoting what passed (severity 0). A generator that cannot measure the site at
   all drops the lead. probe never falls back to a template.
2. **Suppression is global and permanent.** Unsubscribe, complaint, hard bounce
   or any reply removes that address from every campaign, forever.
3. **Nothing sends without explicit approval.** Campaigns are born paused.
4. **Dry-run is the default.** `PROBE_SEND_ENABLED` must be exactly `true`.
5. **No sends into blocklisted jurisdictions.** `DK` and `DE` today. Everything
   else is contactable, including a lead whose country could not be established,
   and the loader refuses to start if `DK` ever leaves the blocklist.

Two database indexes carry most of the safety: `sends_email_hash_uniq` makes
contact-once a constraint violation rather than a race condition, and
`leads_domain_uniq` stops the same product appearing three times because it
launched on three directories.

Contact-once is enforced twice, because the two layers fail differently. The
send claim is an atomic `queued -> sending` UPDATE, so two probe processes cannot
dispatch the same row. The Day3 call carries the send row's id as its
`Idempotency-Key`, so one process cannot double-send across an ambiguous network
failure: Day3 replays the original response instead of accepting a second
message.

## Layout

```
probe/
├── apps/
│   ├── web/        Next.js on Vercel: dashboard, approval queue, /u, /c,
│   │               /hooks/day3 (delivery events), /hooks/ses (inbound replies)
│   └── worker/     Node + node-cron on a VPS under systemd: sweep, resolve, generate, send
├── packages/
│   ├── config/     probe.toml loader, env validation, send preflight, logger
│   ├── core/       hashing, HMAC, generator contract, copy lint, footer, MIME, pacing,
│   │               jurisdiction, matching, Day3 + SNS webhook verification
│   └── db/         schema.sql, migrations, typed queries
├── probe.toml      committed config; seeds the database, never read at runtime
├── PLAN.md         the specification
└── docs/
    ├── CONTRACTS.md  cross-package API
    └── RUNBOOK.md    Day3, DNS, deploy, going live, and what to do when it misbehaves
```

**probe holds no AWS credentials.** It sends through Day3's transactional API
(`POST /api/v1/emails`), on the SES account, verified domains and reputation Day3
already owns and that exit1's own mail runs on. Delivery, bounce and complaint
come back as a signed webhook to `/hooks/day3`. The one thing Day3 does not do is
receive, so replies still arrive over SES inbound to `/hooks/ses`, and a reply
inserts a suppression before anything else happens.

The trade is that Day3 assembles the MIME envelope, so the `.eml` in `/queue` and
`./outbox` is a faithful preview rather than the exact bytes. Subject, both
bodies and the unsubscribe target are byte-identical to what is sent. See
PLAN.md §5.1.

The split is deliberate. Vercel gets everything that must answer instantly and
must never be down, unsubscribe above all. The VPS gets everything long-running:
pacing a send queue over a seven-hour window is a daemon, not a serverless
invocation.

## Getting started

```bash
pnpm install
cp .env.example .env          # fill in SUPABASE_DB_URL, PROBE_HASH_PEPPER, PROBE_HMAC_SECRET
pnpm build                    # tsc -b for config, core, db, worker
pnpm migrate                  # applies packages/db/migrations to SUPABASE_DB_URL
pnpm seed                     # upserts probe.toml campaigns into the campaigns table
pnpm test                     # vitest
```

`.env.example` marks the four variables that decide whether a real email can
leave. `pnpm --filter @probe/worker cli preflight` checks all of them and says
what is missing, which is faster than reading the file twice.

Generate the two secrets with:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

`PROBE_HASH_PEPPER` never rotates. Rotating it orphans every suppression row,
which means every person who opted out becomes contactable again. Treat it the
way you would treat a private key you cannot re-issue.

### The dry-run harness

Build this first and live in it. It writes real `.eml` files to `./outbox`,
runs the copy lint on every one, and cannot reach Day3:

```bash
pnpm dry-run
```

Open the results in a mail client. Iterating on generator output for two weeks
without a single real send is the entire point of M0.

### Running the pieces one at a time

```bash
pnpm --filter @probe/worker cli sweep      # sweep the enabled sources
pnpm --filter @probe/worker cli resolve    # jurisdiction gate, match, contact cascade
pnpm --filter @probe/worker cli generate   # call generators for matched leads
pnpm --filter @probe/worker cli send       # one pacing tick, honours every gate
pnpm --filter @probe/worker cli autopause  # evaluate the §5.5 thresholds
pnpm web:dev                               # the operator console on :3000
```

And the operator commands, which exist because their absence was the difference
between a runbook step and a runbook wish:

```bash
pnpm --filter @probe/worker cli preflight        # everything that must be true to send
pnpm --filter @probe/worker cli warmup exit1     # start the curve. Until this, the cap is 0
pnpm --filter @probe/worker cli stuck            # sends left mid-dispatch by a crashed worker
pnpm --filter @probe/worker cli hash  a@b.com    # peppered hash, for a GDPR request
pnpm --filter @probe/worker cli erase a@b.com    # GDPR erasure by address or hash
pnpm --filter @probe/worker cli smoke https://their.site --to you@example.com
                                                 # the whole pipeline end to end, mail to you
pnpm --filter @probe/worker cli reconcile        # apply changed rules to existing leads
```

## Daily shape

| Time (Europe/Copenhagen) | What runs |
|--------------------------|-----------|
| 06:30 | sweep the launch directories |
| 07:00 | resolve jurisdiction, match a campaign, resolve a contact |
| 07:30 | call the generators |
| every 10 min, 06:00 to 23:00 | poll generator work that is still running |
| 09:00 to 16:00, weekdays | the send daemon, one pacing loop per sending subdomain |

Between 07:30 and whenever Morten opens `/queue`, nothing moves. That is by
design: approval is a human gate and there is no timeout on it.

## Configuration

`probe.toml` is committed and seeds the database. On worker boot each
`[campaigns.*]` block is upserted by slug: static fields are overwritten from
the file, and runtime-mutable state (`paused`, `warmup_start`) is never touched.
Everything at runtime reads the table, so there is exactly one source of truth
per field and no drift.

Secrets live in the environment only. See `.env.example` for the full list.

## Testing

```bash
pnpm test           # unit tests across packages and the worker
pnpm typecheck      # tsc -b everything, then the Next app
```

There is no test that talks to a live database. Anything database-shaped is
guarded behind `SUPABASE_DB_URL` being set.

## Before the first real send

Everything below is a hard prerequisite, not a checklist to work through
opportunistically.

- Legal review per PLAN.md §9.4. Four concrete questions, one lawyer hour. The
  only item here you cannot do yourself.
- `postal_address` in `probe.toml` filled in with a real address. CAN-SPAM
  requires it, and the copy lint blocks every email until it is there. `pnpm
  dry-run` shows the failure on every fixture while it is still a placeholder.
- A Day3 account with the sending subdomain verified under Domains, an API key,
  and a webhook endpoint on `/hooks/day3`, per §5.1. No separate AWS account and
  no SES production access request.
- An SES inbound receipt rule so replies land somewhere real, per §5.3, with its
  topic ARN in `SNS_ALLOWED_TOPIC_ARNS`.
- Cloudflare Access in front of the dashboard with its AUD tag configured, per
  §9.3, plus Vercel Deployment Protection so the origin is not reachable
  directly.
- `cli warmup <slug>`. Without a `warmup_start` the daily cap is 0 and nothing
  sends, however much is queued. The dashboard shows this as gate 3 of the
  dispatch interlock.

`cli preflight` checks the mechanical half of this list. `docs/RUNBOOK.md` §6 is
the step by step, in order, with the commands.
