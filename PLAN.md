# probe

Internal lead generation and cold outreach sender for Pradsgaard Labs EMV products
(exit1.dev, day3.app).

**Status:** planning
**Owner:** Morten
**Repo:** `C:\Users\morte\Documents\Github\probe`

---

## 1. What this is

One email per person, ever. That email carries a finding about *their* product,
generated by one of our own tools against their public surface, that they can
verify in thirty seconds. If no finding can be generated, no email is sent.

The app does the boring machinery around that: sweeping launch directories every
morning, resolving a contact address, calling out to the right generator,
showing Morten the exact bytes before anything leaves, pacing sends on a warmup
curve, and absorbing bounces, complaints and unsubscribes into a global
suppression list.

## 2. What this is not

- Not multi-tenant. One operator (Morten). No signup, no roles, no billing.
- Not a sequencer. There are no follow-ups. One contact, one email, forever.
- Not a template engine. probe never composes copy. Generators do.
- Not published. If that ever changes, the generator contract (§6) is already
  the right shape and nothing else needs to be.

## 3. Core rules

### 3.1 Invariants

Not preferences. Enforced in the database where possible, not in application
logic, and never relaxed.

1. **No proof, no send.** A generator that returns no finding drops the lead.
   probe never falls back to a template.
2. **Suppression is global and permanent.** Unsubscribe, complaint, hard bounce
   or any reply removes that address from *every* campaign, forever. There is no
   resubscribe path.
3. **Nothing sends without explicit approval.** Campaigns are born paused.
4. **Dry-run is the default.** `PROBE_SEND_ENABLED` must be explicitly true.
5. **No sends outside allowlisted jurisdictions.** A lead whose resolved
   country is not on `allowed_countries` never advances past match, and
   unknown counts as blocked (§9.1). The allowlist can grow; the gate itself
   never relaxes, and Denmark is never on it. Blocked leads are still swept
   and stored (§8.1), just never contacted.

Rule 2 is global because exit1 and day3 are the same legal entity writing to the
same human inbox. Honouring an opt-out on one product and not the other is
ignoring the opt-out. It's also self-protective: both campaigns send from the
same probe AWS account, so a complaint from either counts against the
account-level threshold that can throttle both.

### 3.2 Policy: contact once, across all campaigns

**Default on. Reversible. Measured.**

An address that has received one probe email never receives another, from any
campaign. Enforced by `sends_email_hash_uniq` (§7), and only by that index.
Sends never write to `suppressions`, so this policy stays a genuine lever:
relaxing the index relaxes the policy, and nothing else.

This is a judgement call, not a legal or deliverability requirement, and it is
kept separate from §3.1 deliberately.

**Why it's on.** The premise of the email is *I did forty minutes of work
specifically about your product*. A second one, months later, from a different
product of ours, reveals the machine behind it, and the recipient reclassifies
both emails retroactively. That's a worse outcome than the send we didn't make.

**What it costs.** Every lead dropped for this reason is a real lead thrown away.
That cost is unknown until we measure it, so measure it: see §8.2.

**How to relax it, if the number justifies it.** Replace
`unique (email_hash)` with `unique (email_hash, campaign_id)`, keeping the
partial `where` clause, and gate the second send on: no reply and no click on
the first, a twelve-month gap, and still no suppression row. Note that "the
first one got no reply" is weak grounds. If a verifiable finding about their
own product didn't land, a different verifiable finding probably won't either.

## 4. Architecture

```
                    ┌──────────────────────────────────┐

                    │  sources leads contacts          │
                    │  proofs sends events             │
                    │  suppressions                    │
                    └───────▲──────────────────▲───────┘
                            │                  │
        ┌───────────────────┴──────┐   ┌───────┴────────────────────┐
        │  Vercel  (apps/web)      │   │  VPS  (apps/worker)        │
        │  ─────────────────────   │   │  ─────────────────────     │
        │  /            dashboard  │   │  cron  sweep    06:30      │
        │  /queue       approvals  │   │  cron  resolve  07:00      │
        │  /u/:token    unsub      │   │  cron  generate 07:30      │
        │  /c/:token    click      │   │  daemon send    09:00-16:00│
        │  /hooks/day3  events     │   │                            │
        │  /hooks/ses   inbound    │   │                            │
        └──────────▲───────────────┘   └────────┬───────────────────┘
                   │                            │
                   │ signed webhook             │ POST /api/v1/emails
                   │ delivery/bounce/complaint  │ Bearer + Idempotency-Key
                   │                            │
              ┌────┴────────────────────────────▼────┐
              │  Day3                                │
              │  owns the SES account, the verified  │
              │  sending domains and the reputation  │
              └──────────────────────────────────────┘

                                    ┌───────────────────────┐
     SES receive ──► /hooks/ses     │  generators           │
     (replies only, the one         │  exit1.dev  /probe    │◄── HTTPS + HMAC
      thing Day3 does not do)       │  day3.app   /probe    │    from the worker
                                    └───────────────────────┘
```

**Why the split.** Vercel gets everything that must answer instantly and must
never be down, unsubscribe above all. If `/u/:token` 404s while a batch is in
flight, that is a compliance incident, not a bug. The VPS gets everything
long-running: pacing a send queue over a seven-hour window with irregular gaps
is a daemon, not a serverless invocation, and trying to fake it inside Vercel's
execution limits is a losing fight.

**Why Day3 is in the path.** probe holds no AWS credentials (§5.1). Day3 owns
the SES account and the verified domains, and probe is one more caller of its
transactional API, the same one that carries exit1's own mail. The two inbound
arrows are the two halves of the feedback probe needs: `/hooks/day3` for
delivery, bounce and complaint, and `/hooks/ses` for replies, which is the one
part of the mail path probe still owns directly.

**Runtime:** TypeScript everywhere. Next.js on Vercel, plain Node + `node-cron`
on the VPS under systemd. Postgres via Supabase. Both apps talk to the database
server-side only, using the service role key: the worker from its jobs, web
from server components and route handlers behind Cloudflare Access. Nothing
database-facing ever ships to the client, so there is no RLS surface to design.
If web ever grows client-side data access, that decision gets revisited first.

## 5. Sending setup

### 5.1 Sending through Day3

probe does not talk to SES. It sends through **Day3's transactional API**, on
the AWS account, SES identities and reputation that Day3 already owns and that
exit1's own mail already runs on.

An earlier version of this plan called for a **separate AWS account** for probe,
on the reasoning that SES bounce and complaint enforcement is applied at the
account level, so a cold campaign drifting over 0.1% complaints in a shared
account puts exit1's downtime alerts at risk. That reasoning is still correct,
and it is not the whole picture: we own Day3. It is an email sending platform
with per-account suppression, per-account risk status, an admin pause, and
domain verification, and probe is a tenant of it like any other. The isolation
the separate AWS account was buying is bought instead by probe being its own
Day3 account, with its own domains, its own suppression list and its own
sending-enabled flag.

What this removes, none of which was cheap:

- No new AWS account, and no SES production access request with a day of lead
  time.
- No per-product DKIM, custom MAIL FROM or DMARC records to publish. Day3's
  domain verification does that, and it is the same flow exit1 already went
  through.
- No AWS credentials in probe's environment at all.
- No SNS topic or subscription for delivery notifications. Day3 posts a signed
  webhook instead.

What it costs:

- **probe no longer controls the MIME envelope.** Day3 assembles the message
  from the parts probe sends (subject, both bodies, from, reply-to, the
  unsubscribe target). The consequence worth naming: the `.eml` in `/queue` and
  in `./outbox` is a faithful *preview*, not the exact bytes on the wire. The
  content is byte-identical; the envelope is Day3's. `packages/core/mime.ts`
  still exists and is still the one composer, and it is now preview-only.
- **The shared reputation is real.** A complaint against probe is a complaint
  against the SES account exit1's alerts go out on. That is the risk the
  separate account was avoiding, and it is why §5.5's auto-pause is tighter
  here than it would otherwise be: any complaint at all pauses the campaign,
  not just a rate over a threshold.

**probe's send is exactly-once at two layers.** The database claim (§8.6) stops
two probe processes dispatching the same row. The `Idempotency-Key` on the Day3
call, which is the send row's own id, stops one process double-sending across an
ambiguous network failure: Day3 replays the original response instead of
accepting a second message. Neither layer is redundant, because they fail in
different directions.

### 5.2 Domains

| Product   | From                    |
|-----------|-------------------------|
| exit1.dev | `morten@mail.exit1.dev` |
| day3.app  | `morten@mail.day3.app`  |

Root domains are never used for sending. Per-product subdomains so a problem on
one does not contaminate the other.

Each sending subdomain is added under **Domains** in the Day3 dashboard and
verified there. Day3 publishes what DNS records are needed and checks them; any
local part on a verified domain works, with no pre-created sender. A `from_email`
on an unverified domain gets a synchronous `403 domain_not_verified` from the
API, which surfaces in probe as a failed send with that message on the row, not
as a silent drop.

Verify alignment before sending anything real: send one message to a
`mail-tester.com` address and one to a Gmail account, and check that SPF and
DKIM both pass with the right domain in the received headers.

### 5.3 Receiving replies

**Day3 has no inbound side.** This is the one part of the mail path probe still
owns directly, and it stays as it was: `morten@mail.exit1.dev` must be a live
mailbox, with an SES inbound receipt rule writing to S3 and publishing to SNS,
and SNS posting to `/hooks/ses`. A reply that bounces is worse than never
sending.

The receipt rule lives in the Day3 AWS account, since that is where the domain
identities are.

The inbound handler, in order:

1. **Filter auto-replies.** An `Auto-Submitted` header with any value other
   than `no`, `Precedence: bulk` / `auto_reply`, or an `X-Autoresponse` /
   `X-Autoreply` header marks the message as automated. Automated mail is
   forwarded but never suppresses and never counts as a reply. An out-of-office
   must not burn a contact or inflate the one metric that matters.
2. **Suppress.** For genuine replies from a contact address, insert a
   suppression with `reason = 'replied'` before anything else happens.
3. **Forward** to the real inbox either way.

`SNS_ALLOWED_TOPIC_ARNS` is **required**, and the endpoint refuses everything
when it is empty. A valid SNS signature only proves a message came from SNS, not
that it came from our topic: anyone with an AWS account can create a topic,
subscribe this endpoint and post forged bounces, each of which writes a
permanent suppression with no resubscribe path.

### 5.3.1 Delivery, bounce and complaint tracking

Day3 posts a signed webhook to `/hooks/day3` for every message probe sends.
Endpoint configuration lives in the Day3 dashboard; subscribe it to:

```
email.delivered  email.bounced  email.complained  email.failed
```

`Day3-Signature: t=<unix>,v1=<hex>` over `${t}.${rawBody}`, HMAC-SHA256 with the
endpoint's `whsec_...` secret. The verification is the entire security boundary
around every suppression write probe makes, so it fails closed on a missing
secret: the URL is not a secret, and an endpoint that accepted unsigned
deliveries would let anyone who found it suppress arbitrary addresses. That is a
denial-of-leads which would be invisible, because a suppressed lead looks
exactly like a lead that opted out.

**Only a permanent bounce suppresses.** Day3 relays SES's `bounce_type`, and a
`Transient` bounce is a full mailbox or a greylist. Suppressing on one throws
away a real lead that has no resubscribe path, and counting one against §5.5's
*hard* bounce threshold would auto-pause a campaign because a founder went on
holiday with a full inbox. Soft bounces are recorded and never acted on.

Two ids per send, because probe holds them at different times:
`sends.provider_email_id` is Day3's `eml_...`, known the moment Day3 accepts the
message and the join key its webhooks arrive with; `sends.ses_message_id` is the
underlying provider message id, which Day3 relays on the first delivery event
and which is null until then.

Do **not** enable open tracking on the Day3 side. §8.7: Apple Mail Privacy
Protection made the number meaningless and the pixel is a small deliverability
negative for no information. Click tracking is probe's own `/c/:token` redirect.

### 5.4 Warmup and pacing

Fixed warmup curve per sending subdomain, no manual override:

| Days  | Daily cap |
|-------|-----------|
| 1-3   | 5         |
| 4-7   | 10        |
| 8-14  | 20        |
| 15-21 | 35        |
| 22+   | 50        |

Send window 09:00 to 16:00 Europe/Copenhagen, weekdays only.

**Each sending subdomain is paced independently.** They are separate
reputations and one queue must never starve the other.

**Gaps are computed, not fixed-range.** A fixed 4 to 22 minute range averages
13 minutes, which fits about 32 sends in a seven-hour window and can never
reach the 35 or 50 per day caps. Instead, each gap is
`remaining window ÷ remaining quota`, jittered ±40%, floored at 4 minutes.
The floor means the hard ceiling is about 105 sends per subdomain per day,
comfortably above any cap, and early warmup days naturally spread 5 sends
across the whole window instead of clustering them.

**Recipient timezones.** Show HN skews US, and 09:00 to 16:00 Copenhagen is
roughly 03:00 to 10:00 US Eastern, so most sends land overnight for the people
most likely to reply. Acceptable during warmup; once warmed, consider extending
the window into the Copenhagen evening. Per-region scheduling is an M7 concern,
not an M6 blocker.

### 5.5 Kill switches

- `PROBE_SEND_ENABLED=false`: global, checked before every single send.
- **Any complaint at all pauses the campaign**, whatever the rate works out to.
  This used to be an emergent consequence of two constants rather than a
  decision: with a 0.05% threshold and a 20-send volume floor, the first
  complaint after 20 sends is a 5% rate, a hundredfold over the line, so it
  paused anyway. Emergent is the wrong way for a rule this consequential to
  exist, because the operator reads the pause reason and has to recognise it as
  intended. It is now explicit, and it is right: the threshold only starts
  meaning anything around 2000 sends, and at probe's volumes one person calling
  a probe email spam is a signal about the premise. It matters more here than on
  a dedicated account, because the SES reputation is shared with exit1's alerts
  (§5.1).
- Auto-pause the campaign if the rolling 7-day complaint rate > 0.05% or the
  **hard** bounce rate > 3%. Half of AWS's thresholds, so you find out before
  they do. Hard bounces only: a transient bounce is a full mailbox or a
  greylist, and counting one here would pause a campaign over a founder's
  holiday autoresponder.
- A rate needs a denominator, so the two rate rules do not fire below 20 sends
  in the window. The complaint rule above ignores that floor deliberately.
- Big red button in the UI that flips `campaigns.paused = true` for everything.

## 6. Generator contract

probe never writes copy. It asks a product for a finding.

### Request

```
POST https://exit1.dev/api/probe/generate
X-Probe-Timestamp: 1756...
X-Probe-Signature: sha256=<hex>
Content-Type: application/json

{
  "lead_id": "01J...",
  "product": {
    "name": "Meterbase",
    "url": "https://meterbase.dev",
    "description": "Usage-based billing for API companies",
    "source": "show_hn",
    "launched_at": "2026-09-01T06:00:00Z",
    "tags": ["api", "billing", "developer-tools"]
  },
  "recipient": {
    "first_name": "Priya"
  }
}
```

Signature is `HMAC-SHA256(secret, timestamp + "." + raw_body)`. Generators reject
a timestamp more than 300s old.

Note that `recipient` deliberately does **not** include the email address.
Generators have no need for it, and keeping it out means a generator bug can't
leak contact data.

### Responses

**200: finding produced.**
```json
{
  "status": "ready",
  "severity": 1,
  "subject": "/v1/usage returned 502 on 3 of 20 probes this morning",
  "html": "<html>…</html>",
  "text": "Your /v1/usage endpoint…",
  "fix": "The 502s cluster on requests without an Accept header; your gateway…",
  "evidence_url": "https://exit1.dev/probe/01J...",
  "meta": { "probes": 20, "failures": 3, "window": "06:14-07:49" }
}
```

`severity` is the quality bar, enforced by probe rather than trusted to
generator taste drifting over time. Severity 1 means a founder would thank you:
a broken documented endpoint, a failing signup flow, a certificate expiring
inside 30 days, a 404ing status page. Severity 2 is real but pedantic: TTFB,
missing HSTS on a landing page, long redirect chains. **probe mails severity 1
only.** A severity 2 finding is recorded on the proof and dropped as `no_proof`,
because a weak finding is a pretext, and a pretext is worse than no email for
the recipient, for any regulator reading intent, and for the reply rate.

`fix` is required. The email hands over remediation, not just diagnosis (§9.2).

**202: working on it.** `{"status":"pending","retry_after":300}`. probe
honours `retry_after` (clamped to 60-1800s) and re-polls with the same
`lead_id`. The budget is elapsed time, not poll count: **two hours** after the
first request, the slot is released and the lead dropped as `generator_failed`.
Sized so the exit1 probe run of 60 to 90 minutes finishes with headroom.

**204: nothing found.** Lead is marked `no_proof` and dropped. Not an error;
this will be the majority outcome and that's the point.

**4xx/5xx**: retried 3 times with backoff, then dropped.

probe sends `html` and `text` byte for byte. The only modifications are
appending the footer (§9.2), which is not optional, and rewriting
`evidence_url` through the `/c/:token` click redirect (§8.7). Both body
variants must pass the copy lint (§9.2) before anything reaches the queue.

### Generators

**exit1.dev**: the natural fit. Point the existing probe suite at the product's
public surface for 60 to 90 minutes on launch morning. Candidate findings:
non-2xx responses on documented endpoints, TLS certificate expiring inside 30
days, missing HSTS, redirect chains longer than two hops, TTFB above 1s from
multiple regions, a status page that 404s. Rank by severity, then by how
embarrassing it is on launch day, and return the single best one. Return 204
if nothing clears severity 1. Most sites will be clean or merely imperfect,
and sending anyway is the failure mode.

**day3.app**: TODO. Needs a description of what day3 does before the finding
type can be specified. Stub returns 204 until then.

## 7. Data model

```sql
create type lead_status as enum (
  'discovered','contact_resolved','no_contact','matched','no_match',
  'generating','ready','approved','sent','rejected','no_proof','dropped'
);

-- Note: no 'sent' reason. Sends never insert suppressions; the contact-once
-- policy (§3.2) lives entirely in sends_email_hash_uniq below, so relaxing
-- that index is a real lever and not a no-op.
create type suppression_reason as enum (
  'unsubscribed','complained','bounced','replied','manual'
);

-- Launch directories we sweep
create table sources (
  id            text primary key,          -- 'show_hn', 'product_hunt', …
  name          text not null,
  kind          text not null,             -- 'api' | 'rss' | 'scrape'
  enabled       boolean not null default true,
  last_swept_at timestamptz,
  last_error    text
);

create table campaigns (
  id            uuid primary key default gen_random_uuid(),
  slug          text unique not null,       -- 'exit1', 'day3'
  product       text not null,
  generator_url text not null,
  from_name     text not null,              -- 'Morten Pradsgaard'
  from_email    text not null,              -- 'morten@mail.exit1.dev'
  reply_to      text,
  paused        boolean not null default true,
  warmup_start  date,
  daily_cap     int not null default 50,
  timezone      text not null default 'Europe/Copenhagen',
  created_at    timestamptz not null default now()
);

-- A product that launched
create table leads (
  id            uuid primary key default gen_random_uuid(),
  source_id     text not null references sources(id),
  external_id   text not null,             -- id within that source
  name          text not null,
  url           text not null,
  domain        text not null,             -- normalised, for dedup
  description   text,
  tags          text[] not null default '{}',
  launched_at   timestamptz,
  discovered_at timestamptz not null default now(),
  jurisdiction  text,                      -- ISO 3166-1 alpha-2; null = unknown
  jurisdiction_source text,                -- 'tld' | 'imprint' | 'hn_profile' | …
  status        lead_status not null default 'discovered',
  campaign_id   uuid references campaigns(id),
  drop_reason   text,                      -- see §8.2; never overwrite once set
  notes         text,
  unique (source_id, external_id)
);
create index leads_drop_reason_idx on leads (drop_reason, discovered_at);

-- Same product on three directories is one lead
create unique index leads_domain_uniq on leads (domain);

create table contacts (
  id           uuid primary key default gen_random_uuid(),
  lead_id      uuid not null references leads(id) on delete cascade,
  email        text,                       -- nulled on suppression, see §9
  email_norm   text,                       -- lowercased, +tag stripped; nulled with email
  email_hash   text not null,              -- HMAC-SHA256(PROBE_HASH_PEPPER, email_norm)
  first_name   text,
  method       text not null,              -- 'mailto' | 'hn_profile' | 'findymail' | …
  confidence   int not null,               -- 0-100
  found_at     timestamptz not null default now()
);
-- Scoped per lead, not global: the same founder launching a second product is
-- a real case, and resolution must be able to record the contact so the drop
-- can be attributed (§8.3). The one-email guarantee lives on sends, not here.
create unique index contacts_lead_hash_uniq on contacts (lead_id, email_hash);

-- Global, permanent, hash-only. Raw address is never stored here.
create table suppressions (
  email_hash  text primary key,
  reason      suppression_reason not null,
  created_at  timestamptz not null default now(),
  detail      text
);

create table proofs (
  id           uuid primary key default gen_random_uuid(),
  lead_id      uuid not null references leads(id) on delete cascade,
  campaign_id  uuid not null references campaigns(id),
  subject      text,
  html         text,
  text_body    text,
  evidence_url text,
  meta         jsonb not null default '{}',
  attempts     int not null default 0,
  polls        int not null default 0,     -- observability; budget is elapsed time (§6)
  status       text not null default 'pending',   -- pending|ready|failed|no_proof
  error        text,
  created_at   timestamptz not null default now(),
  ready_at     timestamptz
);
create unique index proofs_lead_uniq on proofs (lead_id);

create table sends (
  id            uuid primary key default gen_random_uuid(),
  proof_id      uuid not null references proofs(id),
  campaign_id   uuid not null references campaigns(id),
  contact_id    uuid not null references contacts(id),
  email_hash    text not null,
  approved_by   text not null,
  approved_at   timestamptz not null,
  scheduled_for timestamptz not null,
  sent_at       timestamptz,
  -- Two ids, because probe holds them at different times (§5.1). Day3's
  -- transactional email id is known the moment Day3 accepts the message and is
  -- the join key its webhooks arrive with; the SES message id is relayed on the
  -- first delivery event and is null until then.
  provider      text,                      -- 'day3' | 'dry-run'
  provider_email_id text,
  ses_message_id text,
  unsub_token   text not null unique,
  click_token   text not null unique,      -- /c/:token → click event → evidence_url
  -- 'sending' is the claim: the pacing loop flips queued→sending in one atomic
  -- UPDATE and only then hands the message to the provider (§8.6).
  status        text not null default 'queued',   -- queued|sending|sent|failed|cancelled
  error         text
);

-- §3.2, enforced by the database rather than by application logic.
-- Partial: a failed or cancelled send releases the slot, so a transient SES
-- error can't burn a contact forever. Retries reuse the existing row.
-- This is the policy lever. Widening it to (email_hash, campaign_id) is the
-- single change that allows a second email from a different product.
create unique index sends_email_hash_uniq on sends (email_hash)
  where status in ('queued','sending','sent');

create table events (
  id          bigserial primary key,
  send_id     uuid references sends(id),
  type        text not null,   -- delivery|bounce|complaint|click|unsubscribe|reply
  detail      jsonb not null default '{}',
  occurred_at timestamptz not null default now()
);
```

Two indexes carry most of the safety. `sends_email_hash_uniq` makes contact-once
a constraint violation rather than a race condition. A retry loop that
double-sends a founder the same probe report is the mistake that would actually
embarrass us, and application-layer dedup is exactly where that bug lives. The
`where` clause means only live sends occupy the slot; a failure or cancellation
frees it, and in-flight retries update the row rather than inserting.
`'sending'` is in that list because the claim window must not free the slot: a
second lead resolving to the same address mid-dispatch would otherwise pass the
contact-once check and produce the one thing this index exists to stop.
Even under the relaxed form in §3.2, the per-campaign unique index keeps that
protection intact. `leads_domain_uniq` stops the same product appearing three
times because it launched on three directories.

Note that the `suppressions` table is what enforces §3.1 rule 2, and it is
checked independently of this index at three points: before contact resolution,
before generation, and again immediately before dispatch. Relaxing the index
never relaxes suppression.

## 8. Pipeline

### 8.1 Sweep, 06:30 daily

Each source is a module exporting `sweep(): Promise<RawLead[]>`. Failures are
isolated; one broken scraper does not stop the rest.

| Source        | Access                                            |
|---------------|---------------------------------------------------|
| Show HN       | Algolia HN API, `search_by_date?tags=show_hn`     |
| Product Hunt  | GraphQL API, needs a token                        |
| DevHunt       | scrape                                            |
| Uneed         | scrape                                            |
| Fazier        | scrape                                            |
| TinyLaunch    | scrape                                            |
| PeerPush      | scrape                                            |
| OpenHunts     | scrape                                            |
| TrustMRR      | scrape                                            |
| BetaList      | RSS                                               |
| Launching Next| RSS                                               |

Start with Show HN and Product Hunt only. Those two are stable APIs and will
carry the first two weeks on their own. Add scrapers once the rest of the
pipeline is proven. Scrapers break quietly and there's no point maintaining
eleven of them before you know the premise works.

Normalise the domain (strip `www.`, lowercase, drop path) before insert so the
unique index does its job.

**Every lead is stored, always.** Jurisdiction gating, matching and suppression
decide what probe *does* with a lead, never whether it is recorded. The swept
list, Danish and German founders included, is an asset in its own right: a
complete picture of who launched, kept even though some of it will never be
contacted by this tool.

### 8.2 Match

**Jurisdiction first.** Resolve the lead's likely country before anything
else: ccTLD, imprint or contact-page address, legal pages, HN profile
location. Record `jurisdiction` and `jurisdiction_source` on the lead either
way, then gate: a country not on `allowed_countries`, or an unresolvable one,
drops the lead as `jurisdiction_blocked` before a single contact lookup or
generator call is spent. Unknown is blocked, not benefit-of-the-doubt, because
misclassifying a German or Danish founder as American is the expensive error.
See §9.1 for why this gate, not the copy, is the load-bearing compliance
control.

Then match. Cheap and rule-based, no LLM. For exit1: the product must have a reachable HTTPS
URL and must not itself be a monitoring or observability tool. Tag-based
exclusion list plus a keyword check on the description. Unmatched leads get
`no_match` and are never contacted.

**Routing.** `leads.campaign_id` is singular. A product belongs to exactly one
campaign, so a lead matching both exit1 and day3 produces one email, not two.
This is where the real decision lives, and it happens before any contact is
resolved or any generator call is spent. Tiebreak, in order:

1. Whichever campaign's exclusion rules the product does *not* trip
2. Whichever generator is more likely to find something (for exit1: does the
   product expose a public API or docs site worth probing?)
3. Round-robin, so neither campaign starves

**Drop accounting.** Every lead that dies before send records why, in
`leads.drop_reason`, and the reason is never overwritten:

| `drop_reason`              | Meaning                                      |
|----------------------------|----------------------------------------------|
| `jurisdiction_blocked`     | Country not on the allowlist, or unknown (§9.1) |
| `no_match`                 | Fits no campaign                             |
| `suppressed`               | Address already opted out (§3.1)             |
| `contacted_other_campaign` | Address already received a probe email (§3.2)|
| `no_contact`               | Cascade found nothing                        |
| `no_proof`                 | Generator returned 204                       |
| `generator_failed`         | 3 failed attempts or 2 hours pending (§6)    |

`contacted_other_campaign` is the one to watch. After a month, count it as a
share of matched leads. Below ~5% the §3.2 policy is free and stays. Above ~25%
there's a genuine decision to make, and it gets made with that number rather
than a guess. Surface the count on `/health`.

### 8.3 Resolve contact, 07:00

Cascade, stopping at the first hit:

1. `mailto:` on the landing page, `/contact`, `/about`, `/imprint`, `/legal`
2. Show HN: the submitter's HN profile `about` field, which very often has one
3. Product Hunt maker profile links → personal site → step 1 against that
4. `security.txt` / `humans.txt`
5. WHOIS, if not privacy-shielded (rarely useful now)
6. Paid single lookup, Findymail or Hunter, as the last resort, capped at a
   fixed monthly spend

MX record check only. Do not run SMTP `RCPT TO` verification: catch-all
configurations make it unreliable and the probing itself can hurt reputation.
Accept the address, monitor the hard bounce rate, suppress on bounce.

Check `suppressions` **before** step 1. Never spend a generator call, or a paid
lookup, on someone already suppressed.

After a hit, hash the address and run two checks before the lead advances:
`suppressions` again (the address found may differ from any checked earlier),
then `sends` for the same hash. A hash with a live send row drops the lead as
`contacted_other_campaign`. The contact row is still written first, so the drop
is attributable, which is what makes the §8.2 measurement possible.

### 8.4 Generate, 07:30

Queue calls the campaign's `generator_url` per §6. Concurrency capped at 3 so
exit1's probe infrastructure isn't hammered by its own outreach tool.

### 8.5 Approve

Nothing is scheduled until Morten approves it in the UI. Approval re-runs the
copy lint (§9.2); a failing email cannot be approved. Approving writes the
`sends` row with `scheduled_for` computed from the pacing schedule.

### 8.6 Send, daemon, 09:00 to 16:00

One pacing loop per sending subdomain (§5.4). Each loop: **claim** the next due
`sends` row for its campaign by flipping it to `sending` in one atomic UPDATE,
re-check suppression and the global kill switch, render the footer and rewrite
`evidence_url` through `/c/:token`, hand to Day3 with the send id as the
`Idempotency-Key`, record `provider_email_id`, set the lead to `sent`, sleep the
computed gap.

**The claim has to be the mutation, not a lock.** An earlier version selected
`FOR UPDATE SKIP LOCKED` inside a transaction that committed before the row was
touched, which released the lock while the row was still `queued` and left
nothing marking it as taken until the provider had already accepted the message.
Two processes -- the daemon plus one `cli send`, or two daemons overlapping
across a restart -- could both claim and both send it. `sends_email_hash_uniq`
cannot catch that: the row already exists, so there is no second insert to
reject. One email per person, ever was resting on nobody having run two senders
yet.

A row left in `sending` by a process that died mid-dispatch is ambiguous: probe
cannot tell whether the message went out. The worker resolves those to `failed`
on boot, which releases the contact-once slot and returns the proof to `/queue`
for a deliberate re-approval. Never re-queued automatically, because a founder
receiving the same probe report twice is the mistake that would actually
embarrass us.

Re-checking suppression at send time matters. An unsubscribe or reply may have
arrived in the hours between approval and dispatch.

### 8.7 Track

Day3 → `/hooks/day3` on Vercel, verified by signature (§5.3.1). Delivery,
bounce, complaint and failure into `events`. **Permanent** bounce and any
complaint also insert into `suppressions` immediately; a transient bounce is
recorded and never acted on.

SNS → `/hooks/ses` on Vercel, verified by signature, for inbound replies only
(§5.3).

`/c/:token` looks up the send by `click_token`, inserts a `click` event, and
302s to the proof's `evidence_url`.

No open tracking. Apple Mail Privacy Protection made the number meaningless and
the pixel is a small deliverability negative for no information. Clicks on
`evidence_url` are the signal that matters (someone who wanted the full log),
and replies are the only signal that really matters.

## 9. Compliance

The strategy in one line: **jurisdiction gating is the legal load-bearing
wall; content design is what wins everywhere else.** They are complementary,
not alternatives, and neither is allowed to lean on the other.

### 9.1 Jurisdiction gating

Good copy does not make cold email lawful in opt-in jurisdictions. The Danish
Consumer Ombudsman's guidance closes every content-based escape route:
"marketing" includes **branding** (merely raising awareness of a company or
product), so an email that names exit1.dev and links to a report hosted on
exit1.dev is marketing no matter how factual the body is. Even emailing someone
to *ask permission* to send marketing is itself illegal marketing in Denmark.
The spam ban covers B2B fully, and fines are calculated per email (reported
cases: 10,000 DKK for 13 emails, 800,000 DKK for ~38,500). Germany is
comparably strict, with a private-enforcement industry on top.

What *does* work is territory. The traditional Danish position is that
marketing with effect solely abroad is governed by the recipient country's
rules, not markedsføringsloven. So:

- **Launch US-only.** CAN-SPAM is an opt-out regime: cold B2B email is lawful
  with truthful headers, honest identification of the sender, a physical postal
  address in the footer, and an unsubscribe honored within 10 days. probe's
  design exceeds all of it.
- **`allowed_countries` is a config allowlist, starting at `["US"]`.** A lead
  resolving to any other country, or to no country, drops as
  `jurisdiction_blocked` (§8.2). The lead itself is always stored (§8.1).
- **Denmark is never allowlisted.** The config loader refuses to start if `DK`
  appears in the list. Cold-emailing your home regulator's jurisdiction is the
  black end of the gray zone.
- **EU countries are added one at a time, only after legal sign-off.**
  Candidates to ask about: France and Ireland (reportedly role-based B2B
  opt-out), the UK (PECR exempts corporate subscribers, but sole traders and
  personal addresses count as individuals, and founders overwhelmingly use
  personal addresses, so treat the UK as unclear). Germany, Italy, Austria:
  opt-in, do not ask, do not send.

### 9.2 The email itself

The test that separates generated value from a disguised pitch: **the email
must be worth reading even if exit1 didn't exist, and it must never ask for
anything.** A pitch asks; a favor doesn't. Concretely:

1. **The finding is the subject line and the first sentence.** No greeting
   fluff, no "congrats on the launch" (that's sequencer-speak and every
   founder's spam filter, mental or otherwise, knows it).
2. **The complete value lives in the body**: the finding, the evidence
   summary, and the `fix` (§6). If they never click anything, they still got
   everything.
3. **The evidence page is a gift, not a funnel.** Public, no signup wall, no
   email capture, no "claim this report" gate, no retargeting pixel. Normal
   site nav is fine; the conversion mechanism is the quality of the artifact
   and the product being visibly the instrument that made it.
4. **Radical provenance honesty**, which doubles as the GDPR Article 14
   notice: "I run exit1.dev, an uptime monitor. You launched on HN this
   morning, so I pointed it at your site. I found your address on your
   /contact page. Where your data lives and how to have it deleted: <link>."
5. **Zero asks.** No CTA, no pricing, no trial, no "let me know if", no "happy
   to jump on a call", no closing question. Exactly three links: evidence,
   unsubscribe, data notice. If they want exit1 they'll find it; the restraint
   *is* the pitch.
6. **State the contact-once policy in the email.** "This is the only email
   you'll ever get from me. No follow-ups, no sequence." §3.2 becomes visible
   credibility instead of invisible discipline.
7. **Footer, appended by probe, never by generators**: sender identity and
   physical postal address (CAN-SPAM), one-click unsubscribe, data notice
   link.
8. **A copy lint enforces all of this mechanically.** Lives in
   `packages/core`, runs in the dry-run harness and again at approval (§8.5);
   failure blocks the queue. Checks: forbidden patterns (pricing, "sign up",
   "free trial", "book a call", discount and urgency vocabulary), exactly one
   product mention in the body, required footer elements present, exactly the
   three permitted links. Generators are code, and code drifts; the lint is
   what keeps a future generator tweak from quietly turning informative into
   salesy.

The "inform, don't sell" framing is deliberately **not** load-bearing for
legality (§9.1 explains why it can't be). Its real returns: CAN-SPAM
truthfulness, the GDPR legitimate-interest balancing test, how any official
reads intent if it ever comes to that, and, above all, whether the recipient
replies.

### 9.3 Data protection

- **List-Unsubscribe** and **List-Unsubscribe-Post** headers (RFC 8058), plus a
  visible link. `/u/:token` is one click, no confirmation page, no login.
- Suppression is global and permanent, across every campaign. There is no
  resubscribe path. An opt-out on exit1 binds day3: same entity, same inbox.
- **GDPR applies regardless of recipient country** (Danish controller, Art.
  3(1)). Basis: legitimate interest (Recital 47 recognises direct marketing).
  Obligations: the Art. 14 notice at first contact (the provenance block,
  §9.2.4), and an absolute right to object to direct marketing, which is the
  suppression table.
- Record `method` and `found_at` on every contact, as provenance for a GDPR
  request. Support deletion by email hash across all tables.
- Store only hashes in `suppressions`, and **scrub on suppression**: any
  suppression insert also nulls `contacts.email` and `contacts.email_norm` for
  that hash. Someone who unsubscribes should not leave us holding their address
  in plaintext anywhere. `email_hash`, `method` and `found_at` stay, so
  provenance survives the scrub.
- `email_hash` is `HMAC-SHA256(PROBE_HASH_PEPPER, email_norm)`, not a bare
  SHA-256. An unsalted hash of an email is dictionary-reversible, which would
  make the hash-only claim above decorative. The pepper never rotates; rotating
  it orphans every suppression row.
- The dashboard holds founders' addresses. Put it behind Cloudflare Access.
  Personal data on an unauthenticated public URL is a problem regardless of
  whether anyone finds it.

### 9.4 Legal review, before M6

One hour with someone who knows Danish marketing law, with a four-question
agenda rather than an open-ended worry:

1. Confirm the territorial position: sends with effect solely outside Denmark
   (US recipients) are governed by CAN-SPAM, not markedsføringsloven §10.
2. Which EU countries, if any, are safe to allowlist for this model (France,
   Ireland, UK-corporate are the candidates)?
3. Sanity-check the GDPR legitimate-interest assessment and the Art. 14 notice
   text.
4. Confirm that content design does not change the Danish classification
   (expect yes), so nothing and no one is tempted to rely on it.

This is a legal question, not a technical one, and the downside is a per-email
fine rather than a poor reply rate. Resolve before M6, not after.

## 10. UI

Five screens. Server components, Tailwind, no client state library.

- **`/`**: today's numbers: swept, matched, contacts found, proofs ready,
  awaiting approval, sent, clicks, replies. Kill switch. Warmup day counter.
- **`/queue`**: the approval surface, and the only screen that really matters.
  Rendered HTML on the left, lead context on the right (product, source,
  description, the generator's `meta`). Approve / Reject / View raw `.eml`.
  Keyboard: `j`/`k` to move, `a` to approve, `x` to reject.
- **`/leads`**: filterable table, mostly for debugging why something dropped.
- **`/sends`**: what went out, with per-send events.
- **`/health`**: per-source last sweep and last error, generator success rate,
  rolling bounce and complaint rates against the auto-pause thresholds, the
  `drop_reason` breakdown from §8.2 as a share of matched leads, and
  `jurisdiction_blocked` as a share of swept leads (§15.6).

Auth is Cloudflare Access. No user table.

## 11. Config

`probe.toml`, committed. Secrets in env only.

**probe.toml seeds, the database rules.** On worker boot, each `[campaigns.*]`
block is upserted into `campaigns` by slug: static fields (`generator_url`,
`from_email`, `from_name`, `daily_cap`) are overwritten from the file, and
runtime-mutable state (`paused`, `warmup_start`) is never touched by the seed.
Everything at runtime reads the table, never the file, so there is exactly one
source of truth per field and no drift.

```toml
[global]
timezone      = "Europe/Copenhagen"
send_days     = ["mon","tue","wed","thu","fri"]
send_window   = ["09:00","16:00"]
gap_floor_minutes = 4
gap_jitter    = 0.4
# §9.1. The loader refuses to start if "DK" ever appears here.
allowed_countries = ["US"]
# CAN-SPAM footer requirement (§9.2.7)
postal_address    = "Pradsgaard Labs, <street>, <zip> <city>, Denmark"

[campaigns.exit1]
product       = "exit1.dev"
generator_url = "https://exit1.dev/api/probe/generate"
from_name     = "Morten Pradsgaard"
from_email    = "morten@mail.exit1.dev"
daily_cap     = 50
exclude_tags  = ["monitoring","observability","uptime","status-page","apm"]

[campaigns.day3]
product       = "day3.app"
generator_url = "https://day3.app/api/probe/generate"
from_name     = "Morten Pradsgaard"
from_email    = "morten@mail.day3.app"
daily_cap     = 25
exclude_tags  = []
```

Env: `SUPABASE_DB_URL`, `PROBE_HMAC_SECRET`, `PROBE_HASH_PEPPER` (never rotate,
see §9), `PROBE_SEND_ENABLED`, `PROBE_PUBLIC_URL`, `DAY3_API_KEY`,
`DAY3_WEBHOOK_SECRET`, `SNS_ALLOWED_TOPIC_ARNS`, `CF_ACCESS_*`,
`PRODUCT_HUNT_TOKEN`, `FINDYMAIL_KEY`.

No `AWS_*`: probe holds no AWS credentials (§5.1). `.env.example` is the
annotated list, and `pnpm --filter @probe/worker cli preflight` checks the four
that decide whether real mail can leave, rather than leaving them to be read
twice.

## 13. Build order

**M0: foundation.** Repo, pnpm workspaces, schema applied to Supabase, config
loader + campaign seeding (including the DK-refusal check), `packages/core`
with email normalisation, peppered hashing, HMAC and the copy lint. Dry-run
harness that writes `.eml` files to `./outbox`, runs the lint on every one,
and cannot reach SES. Build this first. It's much harder to retrofit than to
start with, and you'll live in it for two weeks.

**M1: sweep.** Show HN and Product Hunt only. Domain normalisation, dedup, and
jurisdiction resolution. Verify by eye that a morning's output looks like real
launches and that the US/blocked/unknown split looks plausible.

**M2: contact resolution.** Steps 1 to 3 of the cascade. Measure the hit rate
before paying for step 6; if mailto + HN profile gets you above 40% you may not
need paid lookups at the volumes involved.

**M3: generator contract + exit1 generator.** The contract in `packages/core`,
the endpoint inside exit1.dev. This is the piece that determines whether any of
it works, so give it real time.

**M4: approval UI.** Dashboard and `/queue`. Cloudflare Access in front.

**M5: sending.** A Day3 account with `mail.exit1.dev` verified under Domains, an
API key, and a webhook endpoint pointed at `/hooks/day3` (§5.1). An SES inbound
receipt rule for replies in the Day3 AWS account, with auto-reply filtering
(§5.3). Send worker, per-subdomain pacing, unsubscribe, click redirect,
suppression scrub, auto-pause thresholds. No new AWS account, no SES production
access request, and no DKIM records to publish by hand.

**M6: go live, US-only.** Legal review done first (§9.4). Then, in order: a real
`postal_address` in `probe.toml`, `cli preflight` clean, `cli warmup exit1`,
unpause exactly one campaign, and only then `PROBE_SEND_ENABLED=true`. 5/day for
three days. Read every single email before approving. Watch bounces obsessively.
`docs/RUNBOOK.md` §6 is the checklist, in order, with the commands.

**M7: expand.** Remaining sources one at a time. day3 generator once its
finding type is defined. Revisit the send window for US recipients (§5.4).
EU countries onto the allowlist only per §9.1, one at a time.

**M8: public reply channel.** See §14. Only after the email pipeline has
proven the finding quality is consistently worth publishing under our name.

Don't compress M0 into M1. The dry-run harness is what lets you iterate on
generator output for two weeks without a single real send.

## 14. Future add-on: public reply channel

The same finding, delivered as a public comment where the launch happened,
instead of as an email. For `show_hn` leads that means a reply in the Show HN
thread: "I pointed our probe suite at your site this morning and found your
/v1/usage endpoint returning 502s; full log here." Later, possibly X and
Reddit (r/SideProject and friends), each with its own rules.

**Why it's attractive.** It is the fully white version of the entire premise:
no electronic-mail law applies, a Show HN thread is *invited* feedback, and
the HN audience rewards exactly this kind of technical specificity. It also
recovers leads the email pipeline must drop: `jurisdiction_blocked` (a Danish
or German founder can be answered in public even though they can never be
emailed) and `no_contact`.

**Ground rules, when it gets built:**

- Only in the lead's own launch thread, never cold-posted elsewhere.
- One comment per lead, ever. The contact-once principle carries over.
- Same severity-1 bar and the same copy rules (§9.2) minus the footer: the
  finding, the evidence link, the fix, affiliation disclosed in the first
  line, zero asks.
- Never boilerplate. Repeating a template across threads is astroturfing, gets
  the account flagged, and torches the reputation that makes the channel work.
  Every comment goes through the same `/queue` approval as an email.
- Respect each platform's rules and rhythms; per-subreddit self-promo policy
  on Reddit, rate limits everywhere. HN first, others only if HN proves out.

Data model impact is small and deferred: a `channel` column on `sends`
(default `'email'`) when the time comes, with the email-specific columns
nullable for public replies. Not built now; noted so the schema decision isn't
a surprise later.

## 15. Open questions

1. **What does day3.app do?** Needed before its generator can be specified.
2. **What's the realistic contact hit rate?** M2 answers this and it determines
   whether the whole thing sustains 25-50/day or tops out at 10.
3. **Legal review (§9.4).** Four concrete questions for one lawyer hour, before
   M6: the territorial position, the EU allowlist candidates, the GDPR
   legitimate-interest assessment, and confirmation that copy doesn't change
   the Danish classification.
4. **How does the exit1 generator handle a clean site?** Return 204. Expect this
   to be the majority case. If it isn't, the probe is being too generous about
   what counts as a finding, and a weak finding is worse than no email.
5. **How much does contact-once actually cost?** Unknown until day3 has a
   generator and both campaigns run side by side. Revisit once
   `contacted_other_campaign` has a month of data behind it (§8.2). Don't decide
   this in advance.
6. **How many leads does US-only cost?** `jurisdiction_blocked` as a share of
   swept leads, on `/health` next to the §8.2 breakdown. If Show HN is as
   US-heavy as assumed, the number is small; if it isn't, that's pressure on
   the M7 allowlist work and the §14 channel, measured rather than guessed.
